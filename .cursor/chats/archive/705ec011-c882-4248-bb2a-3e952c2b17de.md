## Суть концепции (кратко)

1. **Макро-контекст** → ETF/стабильные монеты/exchange flows (то, что возможно автоматизировать частично).

## Целевая логическая структура бота

Предлагаю мысленно разделить код на слои (папки можно назвать так или близко — это архитектурная схема, не обязательно один коммит).

| Слой | Назначение | Что внутри (концептуально) |
|------|------------|----------------------------|
| **1. Data adapters** | Один интерфейс на источник: Bybit REST/WebSocket, при необходимости Binance/другая пара для спота, платные/on-chain провайдеры | Клиенты API, лимиты, ретраи, нормализация полей → единые DTO |
| **2. Ingestion / stream** | Сведение потоков в одну временную шкалу | По мере роста: простая очередь (Redis) или без неё на старте — планировщик + буферы в памяти |
| **3. Feature engine** | Счётчики «как у фондов»: funding delta, OI delta, whale score (агрегаты), поток стейблов (если есть), CVD, дисбаланс стакана, базис spot–perp | Чистые функции: сырые тики → ряд признаков с меткой времени |
| **4. Regime / confluence** | Правило «не один сигнал»: веса и пороги | Модуль confluence score: сколько столбиков совпало из таблицы из файла |
| **5. ML / scoring (опционально по этапам)** | От rule-based → к XGBoost/LightGBM или простому логистическому скорингy | Выходы: `P_continuation`, `P_fake_breakout`, `risk_liquidation` и т.д. |
| **6. Execution** | То, что уже есть: вход, размер, SL/TP, хедж | Отделяется от данных: только принимает «разрешённые» с высоким скорингом решениями |
| **7. Telegram UI** | Кнопки: режим (агрессивный/консервативный), минимальный confluence, показ последнего score и объяснения | Короткий текст «почему»: какие признаки сработали |
| **8. Observability** | Логи сделок vs score, дамп признаков | Для переобучения и отлавливания шума whale-алёртов |

Связь с вашим репозиторием: смешиваемости с имеющимися **`bot.*` mixin’ами и `TradingBot`** — новые блоки как **отдельные сервисы/модули**, которые главный цикл только вызывает, без смешения «слив данных» и «исполнения ордера» в одной куче.

## Этапы внедрения (практический roadmap)

Согласовано с **PRIORITY STACK** из файла и с вашей инфраструктурой (DO + Telegram).

### Фаза 0 — Основа архитектуры (1–2 недели условно)

- Ввести **контракты данных**: формат «снимок признаков на момент T» для символа.  
- Отделить **сбор признаков** от **решения торговать**.  
- В Telegram: кнопки **минимального confluence** и **dry-run / live** (если ещё нет).

### Фаза 1 — Bybit: деривативное подтверждение (обязательное в стратегии)

- Интеграция/доработка: **funding, open interest, ликвидации** (что доступно по API символу).  
- Признаки: `funding_rate`, `open_interest_delta`, агрегаты по ликвидациям.  
- Rule-based скоринг: например «OI растёт + funding не экстремален».

### Фаза 2 — Рыночный микро-структурный слой (PRO-edge по документу)

- **CVD / агрессивные объёмы** — если технически получаете поток сделок/агрегируете с Bybit или зеркальной бирже.  
- Стакан: **имбаланс**, крупные уровни (упрощённый volume profile / зоны ликвидности там, где данные есть).

### Фаза 3 — «Умные деньги» без иллюзий

- Один-два **внешних источника** с понятными лимитами (например **Whale Alert API**, косвенно — **exchange flow** через Glassnode/CryptoQuant **если платите подписку** — иначе ручные/полуручные вводы через Telegram-кнопку «макро-биас» как временная мера).  
- Преобразовать в **числовые фичи** (`whale_tx_count`, `stablecoin_proxy`, и т.д.), не в «немедленный BUY».

### Фаза 4 — Confluence engine (сердце документа)

- Таблица весов из раздела **Confluence** (накопление + outflow + funding + OI + CVD … — что реально есть в ваших данных).  
- Выход: **`confluence_score` + список сработавших факторов** для сообщения в Telegram.

### Фаза 5 — Signal ranking / AI

- Начать с **простого ранжирования + калибровка порога** по историческим логам.  
- Затем: **LightGBM/XGBoost** на сохранённых фичах (нужна история и разметка: что считали «удачным» входом — из вашего feedback loop, см. ваши скрипты retrain если используете).  
- Выход модели именно **`P(continuation)`** или несколько классов — как в стратегии, не сырая покупка.

### Фаза 6 — Расширение источников (по возможности и бюджету)

- Smart wallet reputation, кластеры кошельков — **только если** есть доступ к labelled данным (Nansen/Arkham и т.д.).  
- Кросс-рынок (ETF, опционы) — для криптобота вторично, можно позже.

### Фаза 7 — Масштабирование потоков (не в первый день)

- **Redis Streams / Kafka** — когда несколько символов, много источников и нужна надёжная доставка. На старте часто достаточно асинхронного Python + одна очередь `asyncio`.

## Ассистент

В вашем **`config.yaml`** имя **`PRD-BOT-NEW`** фигурирует не как «отдельный бренд конфига», а как **удобное имя папки/варианта бота**, куда уже заведены **пути к файлам**:

1. **`entry.trained_model_weights_path`** — веса трансформера после обучения:  
   `bots/PRD-BOT-NEW/models/transformer_weights.pt`  
   Комментарий рядом говорит, что после ночного cron веса лежименно там (старый процесс деплоя/репозитория).

2. **Блок `feedback_loop` (или связанный с датасетами)** — пути к данным переобучения и очереди:  
   `bots/PRD-BOT-NEW/data/...` (`signal_only_feedback_data.json`, `training_data.json` и т.д.) — то есть **рабочее дерево данных** для feedback/retrain было привязано к каталогу с таким именем.

3. **Комментарий про cron** с `cd /root/PRD-BOT-NEW` — это просто **пример пути на сервере**, откуда когда-то гоняли скрипт обзора; на ваш актуальный путь (**`PRD-TELEGRAM-SCORE`** и т.п.) это может не совпадать.

Итого: **`PRD-BOT-NEW` в конфиге — это историческое именование директории `bots/PRD-BOT-NEW/` (модели + данные)**, чтобы не смешивать их с кодом основного дерева. Это не «магический» параметр платформы, а обычные **относительные пути**; если на сервере у вас другая структура, их можно **единожды заменить** на ваши реальные папки (`bots/...,` `models/...`), чтобы не искать модели там, где их нет.

Если нужно — могу предложить конкретную правку `config.yaml` под ваш текущий путь **`PRD-TELEGRAM-SCORE`** или под плоские пути **`models/`** в корне репозитория.

## Критически важно по безопасности

Вы **полностью опубликовали Bearer-токен** CryptoQuant в переписке. Его нужно **немедленно считать скомпрометированным**.

1. Зайдите на [CryptoQuant → settings / API](https://cryptoquant.com/settings/api).
2. **Отзовите (revoke/delete)** этот токен и **создайте новый**.
3. Новый ключ храните **только в `.env` на сервере**, нигде его не цитируете (ни в чате, ни в скриншотах без маскирования).

## Что значит ответ API

Ответ уже однозначный:

```json
"code":403,"message":"forbidden","description":"403 Forbidden: You don't have an authority for this request."
```

То есть **запрос доходит до CryptoQuant, но ваш аккаунт / текущий план не даёт права на этот endpoint** (или токен отозван/ограничен). Это **не ошибка URL** и не баг нашего бота при корректной передаче `Authorization: Bearer …`.

На практике так бывает, если:

- нет платного доступа именно к **Data API / exchange flows** под ваш тарифом;
- токен привязан к другому типу доступа или истёк/отозван;
- в кабинете нужно включить отдельное разрешение (зависит от CQ).

Что можно сделать дальше:

- Уточнить в поддержке **[CryptoQuant](https://cryptoquant.com/)** или в разделе API/плана: включён ли **BTC Exchange Flows (hourly)** для вашей подписки.
- Пока прав нет — в **`config.yaml`** имеет смысл поставить **`signal_intelligence.cryptoquant.enabled: false`**, чтобы бот не упирался в 403 (остальной слой можно оставить на Nansen или отключить весь блок `signal_intelligence.enabled` до появления доступа CQ).

## Про предупреждение pip про `root`

Это общее предупреждение pip: ставить всё под **root** рискованно. Лучший вариант — **отдельный venv**:

```bash
cd ~/PRD-TELEGRAM-SCORE
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Для тестового сервера «как есть» многие оставляют root, но продакшен обычно переводят на venv/docker.

Ещё раз: **перевыпустите JWT в CryptoQuant** и удалите его из любых логов/чата.

## CryptoQuant (`cq_http_403_api_403_forbidden`)

Как и раньше: у токена **нет прав** на этот endpoint (тариф / не тот продукт). Код бота тут ни при чём.


Тогда слой не будет тратить запросы на 403 и не будет считать CQ-вклад (остальное — Nansen, если он работает).

## Nansen: `nansen_bulk_error: null`, но `nansen_by_base: {}`

Ошибки сети нет, а **строк для сопоставления с BTC/ETH/SOL/BNB нет**. Обычно так бывает в трёх случаях:

1. **Нет ключа в окружении**  
   В `.env` в корне `~/PRD-TELEGRAM-SCORE` должно быть что-то вроде `NANSEN_API_KEY=...`.  
   Проверка (ключ не показывайте никому):

   ```bash
   cd ~/PRD-TELEGRAM-SCORE
   grep -E '^NANSEN_API_KEY=' .env | sed 's/=.*/=***/'
   ```

   Если строки нет — Nansen **не вызывается**, кеш пустой.

2. **Ключ есть, но ответ пустой**  
   Token Screener вернул `data: []` (фильтры, кредиты, тариф). Тогда стоит один раз глянуть «сырой» ответ (без публикации ключа):

   ```bash
   # подставьте ключ из .env в переменную, не вставляя в чат
   source .venv/bin/activate
   python3 -c "
   import os, json, urllib.request
   k = os.environ.get('NANSEN_API_KEY')  # или прочитайте из .env
   print('key set:', bool(k and k.strip()))
   "
   ```

   Либо временно добавить в скрипт лог размера `len(rows)` — но это уже доработка.

3. **В ответе нет строк с символами из `map_bases`**  
   В конфиге задано что-то вроде `map_bases: [BTC, ETH, SOL, BNB]`. Если в выдаче screener за выбранный `timeframe` нет таких тикеров (или они под другим именем), словарь останется пустым.
