## 2. Файл риска: `engine/risk_manager.py`

**Зачем файл:** один центр, который решает «можно ли открывать сделку», «сколько объёма», и ведёт учёт убытков за день. Класс **`RiskGuard`** — это и есть «охранник».

**Что внутри по смыслу:**

| Блок | Что делает простыми словами |
|------|----------------------------|
| **`DayStats` / смена дня** (`_ensure_today`) | Каждый новый календарный день сбрасывает дневную статистику (сделки, PnL, часть счётчиков), чтобы лимиты считались «за сегодня». |
| **`record_trade`** | После закрытия сделки: прибавляет PnL за день, считает подряд идущие убытки, может включить паузу после убытка, учитывает «игнорируемые причины» (например `early_exit`, чтобы мелкие выходы не ломали статистику так, как полноценный стоп). |
| **`can_trade(symbol)`** | Главный вопрос «можно ли входить». Проверяет: аварийная остановка, авто-стоп с таймером, кулдаун после убытка (глобально или по символу), кулдауны по серии убытков на символе, лимит сделок в день, лимит сделок по символу за 24 часа. Возвращает пару: `(да/нет, текст причины)`. |
| **`calculate_position_size`** | Считает **объём позиции** от баланса, риска в %, расстояния до стопа, плеча; режет сверху по марже и жёсткому потолку notional — чтобы одна сделка не съела весь счёт. |
| **`get_size_multiplier`** | После серии убытков может **уменьшать** размер следующих входов (`reduction_factor`). |
| **`emergency_stop` / `reset_guard` / `resume`** | Ручная аварийка и сброс блокировок (часть дублирует то, что вы жмёте в Telegram). |
| **`snapshot`** | Сводка для интерфейса: PnL за день, число сделок, заблокирован ли guard и почему. |

## 3. Файл входа: `engine/entry_engine.py`

**Зачем файл:** решает **«идти ли в рынок по этому символу сейчас»** — не размер позиции (это риск-менеджер), а **качество сигнала** и жёсткие фильтры исполнения.

**Главный метод:** `generate_signal(...)`. Он собирает данные с рынка (свечи, цена, анализ, ордерфлоу, трансформер, зоны, фандинг и т.д.) и возвращает объект **`EntrySignal`**: зайти или нет, сторона, цены SL/TP, уверенность, причины/метаданные.

**Логика по шагам (упрощённо):**

1. **Проверка чисел** — если какой-то показатель битый (не число), сигнал отклоняется (`invalid_metric_type`). Это защита от мусора с биржи.
2. **`market_analysis.can_trade`** — если анализатор рынка сам сказал «сейчас нельзя», выходим сразу.
3. **Опционально** — нейтральный 4H-тренд, слишком низкая волатильность.
4. **Жёсткие фильтры исполнения** — слишком широкий спред; слишком высокий модуль фандинга (с учётом «движущегося» рынка за 24ч).
5. **Набор баллов (scores)** — тренд (4H, структура, свипы), ордерфлоу (нормализованный дисбаланс), вклад модели/AI; веса задаются в классе (в коде сейчас, например, `W_TREND = 0.40` и т.д. — в шапке файла описание v6 чуть расходится с цифрами в классе, это нормальная «эволюция» комментариев vs кода).
6. Дальше по файлу — проверки RR, зон (FVG/OB), опционально обученная модель и финальное решение `should_enter` / уровни SL/TP.

## 3. Есть ли **золотая середина**?

Да, как **политика**, не как один волшебный файл:

1. **Один бот — одна логика:** не обязательно держать два живых контура на одном счёте; проще **одна копия кода** и два **профиля конфига** (например `config.scalp.yaml` / `config.balanced.yaml`).

2. **«Середина» между «поймал DOGE» и «слил на альте»:**  
   - оставить **увеличенное окно по МСК**, как вы хотели, **но**  
   - **убрать `12` (и при желании `21`) из всех списков `block_entry_utc_hours`** в `trading` и в **`strategy_presets.defensive`** (и при необходимости `impulse`), чтобы не простаивать в 15:00 МСК;

   - при необходимости **`strategy_presets.enabled: false`** как у PRD-SCALP — меньше переключений порогов, проще поведение;  
   - **качество входа** держать **средним**: не максимально мягкий `quality_gate` и не полный «развал» ордерфлоу.

3. **Удачный DOGE** на скрине **не гарантируется** копированием PRD-SCALP: это может быть один удачный тренд + тайминг выхода. Важно смотреть **десятки сделок** и **просадку**, а не одну иконку в истории.

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.failures = 0
        self.state = "closed"  # closed, open, half-open
        
    async def call(self, func, *args):
        if self.state == "open":
            raise CircuitOpenError()
        try:
            result = await func(*args)
            self.failures = 0
            return result
        except Exception as e:
            self.failures += 1
            if self.failures >= self.failure_threshold:
                self.state = "open"
            raise

## Ассистент

## `symbol_rank_by: turnover` vs `momentum`

Оба режима только **выбирают, какие пары попадут в топ** из тех, что бот уже считает подходящими (достаточно ликвидности и т.п.). На логику самих **сигналов входа** это не меняет — меняется **список символов**, которые бот каждый цикл смотрит первыми.

### **turnover** (топ по обороту за сутки)
- Сортировка по **денежному обороту за 24 часа** на Bybit (то, что в API обычно называют что-то вроде **turnover24h** — сколько **USDT** прошло через торги).
- В топ попадают **самые «толстые» по деньгам** рынки: чаще BTC, ETH, крупные альты.
- Плюс: обычно **уж уже спред, глубина стакана, меньше дичи** на экзотике.
- Минус: иногда **меньше резких движений** на втором эшелоне монет (если вам нужен именно «импульсный» скан).

### **momentum** (старый режим)
- Сортировка по схеме вроде **объём × модуль суточного изменения цены** (`|изменение % за 24h|`).
- В топ чаще попадают монеты, которые **уже сильно пошевелились** за сутки.
- Плюс: больше **движения и потенциала для скальпа/импульса**.
- Минус: выше доля **волатильных альтов** — шире спред, проскальзывание, больше ложных сигналов.

### Кратко
| | **turnover** | **momentum** |
|---|--------------|--------------|
| Кого поднимает в топ | Крупнейший **денежный** оборот | Сильнее **движение** при объёме |
| Для кого удобнее | Спокойнее, ликвиднее пары | Агрессивнее, «горячие» пары |

У вас сейчас **`turnover`** — это разумный выбор для **стабильности и исполнения ордеров**; **`momentum`** — если целенаправленно хотите больше волатильных кандидатов и готовы к более жёстким фильтрам и просадкам.

```bash

pgrep -af main.py
kill <нужный_pid>
rm -f bot.pid
nohup python main.py >> bot.log 2>&1 &
```

Имейте в виду **watchdog** каждые 2 минуты — он может снова поднять процесс; это нормально, если вы сами бота убили.

Кто-то **перезаписал** лог, например:

## Про «двойной» CYCLE 19 и битые строки в логе

Так бывает, если:

- в **одну и ту же** `bot.log` пишут **два процесса** из **одного каталога**, или  
- лог **обнуляли** `>` и параллельно кто-то ещё писал, или  
- при копировании из терминала строки **смешались**.

У **PRD-SCALP** и **PRD-BOT-NEW** свои каталоги → обычно **разные** `bot.log`. Но если вы когда-то запускали **два раза** из **одной** папки — будет каша в **этой** `bot.log`.

Проверить, **откуда** реально стартовал процесс:

```bash
readlink -f /proc/64477/cwd
readlink -f /proc/63862/cwd
tr '\0' ' ' < /proc/64477/cmdline; echo
tr '\0' ' ' < /proc/63862/cmdline; echo
```

## Что сделать практично

1. **Решить:** нужны **оба** бота на **одном** аккаунте или нет. Если нет — один остановить:

   ```bash
   kill 64477    # если это лишний PRD-BOT-NEW
   # или
   kill 63862    # если лишний PRD-SCALP
   rm -f ~/PRD-BOT-NEW/bot.pid ~/PRD-SCALP/bot.pid
   ```
   Потом оставить **один** запуск `nohup ... >> bot.log 2>&1 &` в **нужной** папке.

2. Лог **не затирать** одним `>` — лучше **`>> bot.log`** или разные файлы: `bot-prd-new.log` / `bot-scalp.log`.

3. **Watchdog** (`*/2 * * * *`) может снова поднять процесс, если считает, что бот «упал» — после остановки проверьте через минуту: `ps aux | grep main.py`.
