📊 Что такое Open Interest (в прикладном смысле)

OI = количество открытых контрактов в рынке.

📈 OI растёт → в рынок заходят новые деньги
📉 OI падает → позиции закрываются (ликвидации / фиксация)

Важно: OI не показывает направление, только силу участия

🧠 БАЗОВАЯ ЛОГИКА (которую должен понимать бот)
1. Цена ↑ + OI ↑ → СИЛЬНЫЙ ТРЕНД

➡️ Лонги наращиваются
➡️ Подтверждение движения

👉 Это лучший сценарий для входа

2. Цена ↑ + OI ↓ → СЛАБЫЙ РОСТ

➡️ Закрывают шорты (short covering)
➡️ Новых покупателей нет

👉 Ловушка → НЕ входить в лонг

3. Цена ↓ + OI ↑ → ДАВЛЕНИЕ ШОРТОВ

➡️ Открываются новые шорты
➡️ Тренд вниз усиливается

👉 Хорошо для входа в шорт

4. Цена ↓ + OI ↓ → ФИКСАЦИЯ

➡️ Закрывают лонги
➡️ Движение выдыхается

👉 Возможен разворот

## Итог реализации

### 1. **Данные с Bybit**
По-прежнему используется ваш же эндпоинт `GET /v5/market/open-interest` в `get_open_interest_history` (интервалы `5min` и `15min`, лимит 8). Тикер для funding и этот вызов выполняются **одним** `asyncio.gather`, чтобы не усиливать rate limit.

### 2. **`analysis/open_interest.py`**
Считает:
- относительное изменение OI по двум последним бакетам (5m и 15m),
- `oi_trend_strength`, `oi_price_divergence` (согласованность движения цены за 5 баров текущего ТФ и ΔOI за 5m),
- флаг «спайка» (|ΔOI 5m| или |ΔOI 15m| ≥ 8%, настраивается в движке).

### 3. **`FeatureEngineer`** (`analysis/feature_engineering.py`)
В конец каждого шага последовательности добавлены 4 признака:  
`oi_change_5m`, `oi_change_15m`, `oi_trend_strength`, `oi_price_divergence` ( transformer получает их в векторе; размер признаков с **15 до 19**).

### 4. **`EntryEngine`** (`engine/entry_engine.py`)
- После выбора `BUY`/`SELL`:
  - **ловушки**: рост цены за ~5 баров при **отрицательном** ΔOI блокирует **лонг** (`short_cover`); для **шорта** — падение цены при отрицательном ΔOI (`weak_trend`);
  - **мягкая оценка**: к composite добавляется `oi_score_weight * oi_signal` (по умолчанию до **0.2**), с усилением при спайке;
  - **риск**: при спайке OI и ATR ≥ `oi_high_volatility_atr_pct` в метаданные пишется `oi_risk_size_mult` (по умолчанию **0.55**).

### 5. **`analyze_entry_mixin`**
Строит `oi_pack`, передаёт его в фичи и в `generate_signal(..., oi_features=...)`. Для скальпа вызывает те же OI-жёсткие правила через `open_interest_scalp_gate`. После загрузки тикера подставляет в сигнал реальный **`funding_rate`**.

### 6. **`entry_exec_mixin`**
Умножает расчётный `qty` на `oi_risk_size_mult` (ограничение 0.25…1).

### 7. **Тест**
Обновлён `backend/tests/test_quant_modules.py` под **19** признаков — тесты проходят.

## Настройка в `config.yaml` (секция `entry:` при необходимости)

Пример «как вы просили» (строже подтверждение по OI ≥ 2% и funding-тильт) — включайте точечно, иначе кандидатов станет мало:

```yaml
entry:
  oi_filter_enabled: true          # главный выключатель
  oi_score_weight: 0.2             # вклад в composite
  oi_spike_pct: 0.08               # порог спайка (доля)
  oi_spike_bonus: 0.35             # добавка к oi_signal при спайке
  oi_trap_long_enabled: true
  oi_trap_short_enabled: true
  oi_min_price_move_frac: 0.0006   # фильтр «шум»: ~0.06% по close за 5 баров на вашем TF
  oi_confirmation_min_frac: 0.02   # нужен для require_positive_* (2%)
  oi_require_positive_for_long: false   # true = как в тексте про ≥2%
  oi_require_positive_for_short: false
  oi_strict_skip_negative: false   # true = режет любой вход при ΔOI5m < 0 (очень жёстко)
  oi_require_funding_align: false  # true = long только при funding > 0, short при < 0
  oi_high_volatility_atr_pct: 1.8  # «высокая» волатильность (как market.atr_pct)
  oi_spike_size_mult: 0.55         # уменьшение объёма при спайке+высокая волатильность
```

Если секции `entry:` в файле нет, `BotConfig` подставит значения по умолчанию из кода (как перечислено в `EntryEngine.__init__`).

## Важно по смыслу

- OI **не даёт направление сам по себе** — он подтверждает или разваливает вашу уже выбранную сторону; ловушка «рост + отток OI» отсекается для лонга.
- Связка **OI + ликвидации** у вас уже есть на уровне ликвидности/ордербука; отдельного «OI × liq stream» в код не добавлял — это можно вынести отдельным шагом.
- При ошибке API OI пакет считается «недоступным» — **жёсткие** OI-фильтры не блокируют вход (чтобы бот не «молчал» из‑за сбоя данных).

Если нужно, могу под ваш стиль торговли подобрать конкретные флаги (`oi_require_positive_for_long` / `oi_require_funding_align`) и пороги под ваш `candle_interval`.

## PRD-SCALP: проблема в `is_running()`

Сейчас вы считаете «бот работает», если любой процесс с **`PRD-SCALP/main.py`** и cwd = репозиторий.

Значит, если когда‑то запустили **`main.py` без флагов** (Telegram‑агент) из той же папки, cron увидит **«уже работает»** и **не поднимет торговый** бот, хотя нужного процесса с `--trading-bot` может не быть.

**Надёжнее:** считать «работает» только процесс с **`--trading-bot`** в командной строке.

Замените функцию на такую логику (идея, можно целиком вставить):

```bash
is_running() {
  local pid
  for pid in $(pgrep -f "$BOT_DIR/main.py" 2>/dev/null || true); do
    [ -r "/proc/$pid/cwd" ] || continue
    [ "$(readlink -f "/proc/$pid/cwd" 2>/dev/null)" = "$BOT_DIR" ] || continue
    tr '\0' ' ' < "/proc/$pid/cmdline" 2>/dev/null | grep -q -- '--trading-bot' || continue
    return 0
  done
  return 1
}
```

Тогда ручной `main.py` без флагов не будет блокировать автозапуск торговли.

## Почему строки в `bot.log` были **дважды**

Запуск через cron/watchdog обычно такой:  
`nohup python main.py … >> bot.log 2>&1`

Тогда **stderr и так пишет в тот же файл**, что и `bot.log`.  
Программа **дополнительно** открывала второй обработчик **`FileHandler(bot.log)`**. В итоге одна и та же запись уходила в **два дескриптора на один файл** — в логе она выглядела как **две одинаковые строки**.

**Исправление:** в `bot/trading_bot_imports.py` добавлена проверка: если stderr указывает на **тот же inode**, что и `bot.log`, **второй `FileHandler` не вешаем** — остаётся один канал записи.

После деплоя и перезапуска бота дубли должны пропасть.

## Почему **404** по `http://127.0.0.1:11434/api/generate`

Это **локальный Ollama** (модели Gemma).  
**404 Not Found** значит: на этом адресе **нет нормального Ollama** (ничего не слушает, или другой сервис без `/api/generate`).

На VPS **чаще всего Ollama не установлен**, а в вашем **`config.yaml` на сервере`, скорее всего, включён блок **`gemma:`** (`enabled: true`). Тогда бот всё равно стучится в `127.0.0.1:11434` и получает ошибку.

**Что можно сделать (любой один вариант):**

1. **Проще всего** — если локальную Gemma вы не используете, в `config.yaml`:
   ```yaml
   gemma:
     enabled: false
     ...
   ```

2. **Если хотите локальную Gemma** — на сервере установить и запустить [Ollama](https://ollama.com/), затем хотя бы:  
   `ollama pull gemma2:2b` и убедиться, что служба слушает `127.0.0.1:11434`.

В коде дополнительно:
- если в YAML **нет** ключа `enabled`, Gemma по умолчанию **выключена** (`from_config`);
- для 404 в лог добавлена **понятная подсказка**, что делать.

## 1. `Market scan done: candidates=107 setups=0 notified=0`

## 2. `Got difference for channel …` (Telethon)

Это служебные сообщения библиотеки **Telethon**: канал **обновился** (новые сообщения, иногда служебные правки).

Сделки/уведомления по каналам идут только когда **текст сообщения** проходит разбор сигнала и дальше ваши настройки (`auto_execute`, лимиты, OpenRouter и т.д.).
